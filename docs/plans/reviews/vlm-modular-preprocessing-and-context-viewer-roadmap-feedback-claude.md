# Feedback: VLM eval roadmap — modality-adapter ContextBlocks + leaf selectors + config-context viewer (Fresh Claude Code review)

## Verdict
**Revise.** The framework/viewer/selector design is sound, well-researched, and implementable, and most of the specific claims verify cleanly against code. But the plan declares "no blocking preconditions remain," and that is not true: the `meds_tools` pin is a heavy transitive-dependency web with a likely-spurious `py>=3.14` floor, the EHR serializer the plan wants to "lift into an inference-time adapter" is today an **offline** materialization step, and the `inline_by_timestamp` fail-closed mechanism has no place to live in the current model layer. These three are asserted-resolved but are actually open.

## Critical Gaps

- **CRITICAL | The `meds_tools` "pin v0.1.0 @ e2a2a59" is not a simple pin — it drags a VM-hostile dependency web, and the `py>=3.14` floor is almost certainly spurious.** The plan (OQ-G, lines 114, 474, 530-536) treats adoption as "pin the SHA + verify `requires-python >=3.14` on the VM." Reality from `meds_tools/pyproject.toml`: `requires-python = ">=3.14"` while the actual deps are mundane (`pandas>=2.3.3`, `google-cloud-*`, `rapidfuzz`, `jupyter`) — **none of which need 3.14**, so the floor reads as a `uv init` scaffolding artifact, not a real requirement. On a normal vLLM/torch/transformers eval VM (typically 3.11/3.12) this floor will **block install for no real reason**, and the fix is an upstream one-line relax, not upgrading the whole eval VM. Worse, `[tool.uv.sources]` resolves `vistabench = { path = "/home/minwoos/repos/vista_bench" }` and `vista-ct = { path = "/home/minwoos/repos/vista-ct" }` — **hardcoded local paths that won't exist on the eval VM** — plus `meds2text` (git) and `meds_reader`. So `pip/uv install meds_tools@e2a2a59` will not resolve cleanly off-`minwoos`. Also note: **there is no git tag `v0.1.0`** (`git tag` is empty; `git describe` = NO_TAGS) — the pin *must* be by SHA, and the doc's "v0.1.0 @ e2a2a59" implies a tag that doesn't exist. Evidence: `meds_tools/pyproject.toml` (requires-python, `[tool.uv.sources]`), `git -C meds_tools tag` (empty). Required fix: either (a) confirm the eval env already has `meds_tools` working (see next gap — the prep scripts import it, so it may already be installed) and pin by SHA, or (b) reconsider whether to vendor the ~50-line pure-pandas serializer instead of taking the whole dependency — which directly reopens the "no third formatter copy" call (raise to user).

- **CRITICAL | EHR serialization is currently an OFFLINE materialization step, but the plan models it as an inference-time adapter — this is an unresolved layer shift, not a "lift."** The plan's EHR adapter (lines 247-252) is "filter chain → serialize (→ meds_tools) → truncate," implying serialization happens inside the inference-time adapter. But today the serializer (`meds_timeline_utils.py:185`, the local fork *with* `exclude_report=True`/STANFORD skip at `:189,:215-217`) runs **offline** in `src/data_tools/OMOP_meds_query/remove_imaging_report.py:69`, which writes a `patient_string` column to CSVs; at inference `run_bq.py` reads that **pre-serialized string** (`find_bq_timeline_column` → `timeline_col`, then only `truncate_timeline` + concat at `:305,:732+`). So "swap the serializer" is really a **layer decision**: does the EHR adapter (a) re-home the offline prep, or (b) serialize at inference — which would pull a `meds_reader.SubjectDatabase` + ontology `lookup_table` (`patient_timeline.py:2,4,92-114`) into the *inference* VM path that today has neither? Consequence for gate-3 (lines 388-390): it compares two *offline* serializers, but unless the materialized `patient_string` CSVs are regenerated, inference still reads the old strings and the gate proves nothing about the live path. Evidence: `remove_imaging_report.py:31,69`, `run_bq.py:257,305,732`, `meds_timeline_utils.py:185`. Required fix: state explicitly which layer the EHR adapter operates at, and if inference-time, name where the `meds_reader` DB + ontology come from on the VM.

- **CRITICAL | `inline_by_timestamp` fail-closed is decided (OQ-D) but has no mechanism — the capability flag has nowhere to live and the assembler has no way to read it.** Lines 184-199 correctly establish that `create_template` front-loads all images then text (verified: `gemma3.py:43-77`, `qwen3.py:46-73`) and that the assembler must "fail closed with a clear, documented error" for unsupported models. But: (1) `BaseVLMAdapter` (`base.py:33-70`) has **no capability field**, and `MODEL_REGISTRY` (`models/__init__.py:6`) is a bare `{type: AdapterClass}` map with no metadata — so "declare `inline_by_timestamp: unsupported`" is net-new with no specified home. (2) The assembler lives in `src/context/`; the capability is a property of `src/models/` adapters — the plan never says how the context package learns a models-package capability without creating a cross-package import cycle, nor **when** the error fires (assembly time vs. a preflight check). (3) There are **8 adapters** in `MODEL_REGISTRY` (gemma3, intern, gemma3-2, qwen3vl, octomed, qwen2vl, qwen2_5vl, medvlm, lingshu, llava, llavamed) but the plan only rewrites `create_template` for **2** (gemma3/qwen3, line 197) — so the fail-closed path is the *common* case (6+ models), not the exception, which raises the bar on specifying it. Evidence: `base.py:33-70`, `models/__init__.py:6-64`, `gemma3.py:43-77`, `qwen3.py:46-73`. Required fix: specify the flag (e.g. `supports_inline: bool` class attr on `BaseVLMAdapter`, default `False`), the read path (assembler receives the resolved adapter or a capability dict, not a bare model_type), and the raise point (preflight, before any weights load, so the viewer also benefits).

## Failure Modes

- **Golden gate 1 relies on CSV row order that `run_bq.py` does not guarantee.** The plan asserts "stable CSV ordering" (line 381) and joins on `index`/`person_id`. But `run_bq` writes rows as processed and *appends* on resume (`:722-731`); nothing pins deterministic output order across a refactor that changes batching. Add: the golden harness must **sort by `(person_id, index)` before diffing**, not rely on file order. `index` is unique per output file (it backs the resume `set()`), so it is a valid join key — but ordering must be imposed by the harness.
- **Gate-3 allowlist lists "ordering" as an acceptable diff — that is safe for intra-line field order but *unsafe* for event/line order, which `inline_by_timestamp` depends on.** Line 390 allowlists "ordering." If that means event/line order can differ between the fork and canonical serializer, then inline placement (which keys off `metadata.timestamp` / event order) could silently differ. In fact both serializers iterate the df in chronological order (`get_described_events_window` returns a time-sorted index; `get_llm_event_string` iterates rows), so event order *should* be stable — clarify that the allowlist "ordering" means **within-line field order only**, and assert event order is identical.
- **`summarize` and the meds_tools serializer both carry silent fallbacks that mask upstream errors** — a pattern `claude_ops.md` says to make an explicit decision, not assume. `_summarize_timeline_for_context` returns the **raw timeline on any exception** (`iterative_retrieval.py:92,137`); the lifted serializer path should decide whether the EHR adapter swallows failures the same way or fails loud. Name it.

## Modularity vs. YAGNI

- **`inline_by_timestamp` (+ typed content sequence + capability machinery) vs. `ordered`-only for Phase 1 | Plan builds both now | No named near-term consumer** — every legacy preset assembles `ordered`; the plan's own "small decisions still open" (lines 484-486) do not commit to any inline experiment. Inline is the single most expensive + most underspecified piece (it forces the `create_template` rewrite across models + the fail-closed capability wiring). The uniform `ContextBlock` and the `ordered` assembler are clearly justified by dissolving the god-enum and are *not* over-built; only `inline_by_timestamp` is speculative-until-a-consumer-exists. **Raise to user:** is inline a Phase-1 requirement, or can Phase 1 ship the `ContextBlock`/`ordered` seam with inline deferred to a Phase-1.5 once a real interleaving experiment is named?
- **Leaf-only vs. re-adding study/series selection later | Plan drops the hierarchy (OQ-A) | Honest trade is understated** — the leaf-only call is **code-supported**, not just asserted: vista_bench selects one imaging row per person upstream (`vista_bench/src/vistabench/queries.py:531` and `progression_recurrence_survival.py:124`: `drop_duplicates(subset=["person_id"])`; `queries.py:589` QUALIFY "prefers visits with imaging"), and each task row carries a single `nifti_path` (`vqa_dataset.py:161-162`) + single slide. So the assumption **holds**. But the plan says the re-add seam is "the selector signature stays generic enough" (lines 30-31, 170-172) — that understates it: the upstream dedup means **candidates for a study-level selector no longer flow downstream**, so re-adding real study selection is a **cross-repo change to vista_bench** (stop deduping, hand multiple candidates through), not just wiring a new local selector. Recommend: cite the corroborating vista_bench code, and state honestly that the re-add cost lives upstream. (Not re-arguing to build it — just documenting the trade accurately.)
- **`summarize` "lift" | Plan calls it a single-function lift | It's a cluster + a fallback** — `_summarize_timeline_for_context` (`iterative_retrieval.py:62-92`) and `_batch` (`:95-138`) are genuinely VLM-wired (take `adapter, model, processor`) ✓, but lifting drags `_run_vlm_text_only`/`_run_vlm_batch`, `_extract_answer`, and `TIMELINE_SUMMARY_TEMPLATE` (from `retrieval.prompt_templates`), and carries the raw-timeline-on-failure fallback. Fine to reuse, but call it a "lift a small cluster," not a one-liner, and decide the fallback behavior.

## Verification Gaps

- **The `meds_tools` precondition is treated as a checkbox but is the likeliest thing to break the build.** "Verify `requires-python >=3.14` on the VM" (line 486) should become: (1) determine whether `meds_tools` is **already installed and importable** in the eval env (the prep scripts import it — so it may be), (2) if not, confirm the eval VM's Python and whether the `>=3.14` floor + local-path `[tool.uv.sources]` can resolve there at all, (3) predefine the fallback (relax the floor upstream, or vendor the serializer) so the executor isn't stuck. Concrete VM recipe: `python -c "import sys; print(sys.version)"; python -c "from meds_tools import patient_timeline; print(patient_timeline.get_llm_event_string.__doc__)"` — expected: prints; **stop** if `ModuleNotFoundError` or a `requires-python`/path-source resolution error.
- **Add a "materialized-strings regenerated" check to the EHR gate.** Because inference reads pre-serialized `patient_string`, the gate must confirm the new serialization is what inference actually consumes — not just that two offline serializers match. VM check: after regenerating the prep CSVs with the new adapter path, assert the `patient_string` column feeding `run_bq` changed (or is byte-identical within the allowlist), then run one smoke and confirm `dynamic_prompt` reflects it.
- **Golden harness ordering recipe (see Failure Modes):** sort both before/after frames by `(person_id, index)` before comparing; assert `index` uniqueness per `(task, experiment)` file.
- The staged golden test is otherwise **behaviorally sound** — it compares `dynamic_prompt` strings, selected indices, and image **hashes** (outputs), plus the adapter-produced prompt/placeholder order per model; the viewer reads selected indices off the assembled block rather than the coarse `used_image` 0/1 (`run_bq.py:831`). No substring-assert-on-generated-source antipattern. One note: `truncate_timeline` (`meds_timeline_utils.py:62`) has a latent quirk — `first_4_rows` is initialized to `''` and never populated, so it prepends `'' + '\n' + full text`. Lifting it **verbatim** is byte-preserving (good for gate 1) — do **not** "fix" it during the lift or gate 1 breaks.
