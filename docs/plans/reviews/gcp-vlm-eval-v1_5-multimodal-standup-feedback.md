## Modularity vs. YAGNI
- Registry exporter | Plan recommends a durable `vista_bench` exporter but leaves it as Open Q1 | Modular alternative + realistic use case: a small exporter beside `TASK_REGISTRY` can generate `valid_tasks_v1_5.json`, text prompts, and image prompts each time bench task metadata changes | Recommendation: prefer the durable exporter if v1_5 includes diagnostic tasks or if this sweep will be repeated; otherwise raise to user because a one-off hand-built JSON is cheaper but fragile.
- Path subsampler versioning | Plan says adapt `subsample_v1_3_path.py` and prefer parameterizing | Modular alternative + realistic use case: rename/generalize to `subsample_path.py` with `--version`, `--bigquery-dir`, `--valid-tasks`, and `--output-base`; future v1_6 only changes CLI args | Recommendation: parameterize; the current function already accepts paths, so the incremental cost is low and it avoids another version-named script.
- Data layout versioning | Plan changes config paths but does not define whether v1_5 uses root folders, `v1_5/`, or legacy cache names | Modular alternative + realistic use case: centralize cohort-version path roots in config and route `resolve_*_path` through them | Recommendation: raise to user if bucket layout is not known; do not silently reuse v1_2/v1_3 names for v1_5 artifacts.
