Steps

Step 1 — presets.py: emit real select chains

_ehr_block(variant) currently only stamps a variant label; this makes it emit the concrete select filter chain per variant (no_img_report = window + code_filter; timeline = [] pending Phase 1; passthrough = untouched).

Files: src/context/presets.py

Verify: structural review only (Mac, no runtime) — confirm the emitted config dict shape matches what EHRAdapter expects.
Step 2 — run_bq.py: _apply_ehr_adapter helper

Updated per Phil's /explain-plan feedback: reuses the existing retrieval.corpus_dir key directly — no separate config step needed (a standalone "add a new config key" step was merged into this one and removed).

New helper called first-line of _build_prompts_for_experiment: resolves each row's LUMIA file via retrieval.corpus_dir (its committed value is a dead contributor-specific path, broken on the real VM — real value set per-VM in the git-ignored overlay, same fix as before, just applied to the existing key instead of a new one), fail-closed drops rows without one (logs the count), then renders survivors via EHRAdapter.ingest()/.contextualize(). context_capture.py shares this method, so golden harness and the viewer get live rendering for free.

Files: src/vista_run/run_bq.py

Verify: structural review (Mac) — confirm the mutation point doesn't disturb the report/path_full branches' column-append logic, which run after it.
Step 3 — docs update

docs/04-running-the-pipeline.md and docs/00-data-setup.md both currently describe the EHR source as the pre-rendered patient_string column — update to describe the live LUMIA path, fail-closed row exclusion, and that retrieval.corpus_dir is now dual-purpose.

Files: docs/04-running-the-pipeline.md, docs/00-data-setup.md

Verify: read-through only.
Step 4 — VM Phase 0: cohort-vs-LUMIA coverage precondition

Derive the eval cohort from the actual loader path (_load_task_data's real BQ+CSV merge), not a hand-authored parallel query — this was a Codex finding: an independently-authored SQL query risks silently diverging from what the eval actually iterates. Join against the LUMIA .xml filenames; also reconfirm the LUMIA schema shape, local corpus reachability, and that the fail-closed guard actually fires.

Expected: coverage_pct + matched/missing counts. Decision gate: >=95.0 proceed; 80.0 to <95.0 proceed with dropped-N called out; <80.0 STOP. Machine: Claude-Code CPU phil-sllm-01. Destructive: no.
Step 5 — VM Phase 1: does the timeline variant need code_filter?

This is where Codex caught the real bug. The originally-drafted gate sampled "N≈20 from Phase 0's covered set" — but since fail-closed filtering runs before the golden harness's sort+limit step, the before/after banks weren't actually guaranteed to draw from the same patients. A missing LUMIA file anywhere in the naive first-20 would cause an index-set mismatch that looks like a gate failure but has nothing to do with code_filter. Fixed by restricting both banks to a Phase-0-confirmed-covered subset before banking, so the fail-closed drop becomes a no-op and the diff is actually testing the right thing.

Expected/Stop: index-set mismatch even on the restricted input → STOP (distinct precondition failure). Strict PASS → no code_filter needed. Strict FAIL → re-bank with code_filter, re-diff. Both pass → default to no-filter, note it. Neither passes → STOP, hand back. Destructive: no.
Step 6 — VM Phase 2: gate-3 allowlist fill-in

Extend to N=20-50 across both resolved variants. Any normalization rule codified into diff_golden.normalize_text must be field-local, event-line-local, preserve line count/order/content exactly, and only normalize numeric equivalence within a bounded tolerance — no catch-all substitutions. --lenient is for local iteration only; the final committed gate must run without it.

PHI-clean readback: report counts/field-names/index-counts only — diff_golden prints raw text previews on failure that must never be pasted into the vm-status doc. Destructive: no.
Step 7 — VM Phase 3: human visual-QA render (the step Phil asked for)

Render N≈5 each of no_image, no_report/timeline_only, and axial_all_image — all three mandatory (a Codex finding: axial_all_image is the only wired preset that exercises CT+EHR composition, so it can't be optional). Structural checks expanded per the prior Phase-2-viewer precedent: non-empty rendered text per card, non-empty token bar, expected image counts, no STOP/traceback text.

Report back: file paths, existence, card counts, exit codes only — never rendered content (PHI). Phil opens the files himself on phil-sllm-01 to actually read them. Destructive: no.
Step 8 — Land

Branch feat/lumia-live-ehr-adapter off main. Landing gate: all 4 verification phases green AND Phil has actually opened and read the Phase 3 HTML — an agent's structural check alone doesn't satisfy this. Also flags two operational notes for whoever runs the first full eval post-landing: use a fresh output tag (resume-by-index could otherwise silently mix pre/post-wiring row counts), and any report comparing these presets to historical full-cohort results should carry the post-drop denominator.

Gotchas

The Phase 1 decision gate wasn't actually self-resolving

iter_captured_examples runs _build_prompts_for_experiment (where fail-closed filtering happens) before its stable-sort + head(limit) step. The "after" bank's first-20 is drawn from already-covered patients; the "before" (legacy) bank's first-20 has no such filtering. If even one of the naive first-20 lacks a LUMIA file, the two banks' index sets diverge and diff_golden hard-fails on index-set mismatch — a precondition failure that looks like (but isn't) a code_filter verdict. Fixed by restricting both banks to a confirmed-covered subset first.

truncate_timeline is not idempotent (moot here, but worth knowing)

An earlier draft of this plan claimed re-truncating already-truncated text was safe/idempotent. Direct code read showed the opposite: meds_timeline_utils.py unconditionally prepends a newline on every call, so calling it twice produces a double newline, not a no-op. Turns out irrelevant here — the fail-closed redesign means every surviving row's timeline text is fully replaced and truncated exactly once — but the false claim was removed rather than left in the doc.

retrieval.corpus_dir is a dead path on the real executor VM

configs/all_tasks.yaml:93 has retrieval.corpus_dir: "/data/fries/datasets/vista_bench_ryan/thoracic_cohort_lumia" — contributor Ryan D'Cunha's own machine-specific path. A prior VM-status doc documents this exact path as absent on phil-sllm-01 (which only has /mnt/su-vista-hot and /mnt/su-vista-uscentral1). This plan's new paths.lumia_corpus_dir key deliberately avoids repeating the mistake — no committed absolute default, VM-local overlay only.

diff_golden --lenient can silently mask real drift

The tool's own flag help text says it "can exit 0 despite text drift." Useful while tuning the Phase 2 normalizer, but the plan explicitly requires the final committed VM gate to run without it and print RESULT: ALL GATES PASS.

Resume-by-index could silently mix row counts after fail-closed lands

_setup_output_and_resume resumes by index. A stale pre-wiring result CSV for one of these presets could silently resume against a mismatched row count now that fail-closed filtering changes N. Flagged as an operational note for the first full (non-smoke) eval run after landing — use a fresh output tag.

Open questions

OQ1 — timeline variant's code_filter scope

Whether the full-timeline preset should also drop STANFORD-tagged codes like no_img_report does was left unresolved in the original design. Resolved via the self-resolving VM decision gate in Step 6/Phase 1 — not a Phil judgment call, an objective byte-diff question.

OQ2 — full-run coverage threshold

Phase 0's >=95%/80-95%/<80% bands are sized for this plan's PFS-1yr smoke. What threshold should gate a full default (multi-task) run once this lands — same bands, or a stricter bar given the cohort-size consequence is now permanent, not just a smoke artifact?

OQ3 — where dropped-row/post-drop-denominator reporting should live long-term

This plan surfaces it via a console log plus the VM handoff doc readback, sufficient for this plan's scope. Should it also become a persisted per-run field (result CSV metadata or a run manifest) so future comparisons against historical full-cohort results can see the denominator without re-reading logs? Out of scope either way — flagging so it isn't silently forgotten.

Claude, re: "this is just input coverage right? we should have it all"
Two distinct things worth separating: Step 4 / VM Phase 0's coverage_pct is purely input coverage — does the raw LUMIA .xml file exist for each person_id, nothing about labels or downstream coverage. This OQ (OQ3) is a separate, secondary question — not whether coverage is complete, but where to persist the dropped-row count for future reference once the check runs. On "we should have it all": that's a reasonable prior, but genuinely unverified — cohort-level LUMIA file coverage has never actually been measured before (only field-level coverage within a 12-patient sample, back in July). That's exactly why Phase 0 exists rather than assuming it — if coverage does turn out to be ~100%, this OQ becomes moot in practice (the denominator barely moves); it only matters if coverage is meaningfully less than complete.
