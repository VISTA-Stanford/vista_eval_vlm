vista_eval_vlm — Step 6: modernize pathology to live vista_bench_v1_6 substrate

Status: Draft (2026-07-21) Owner: Phil Branch (planned): feat/vlm-step6-pathology-live-substrate Source: vlm-step6-pathology-live-substrate.md SHA-256: 905d034c0a58… Generated: 2026-07-21 19:45 UTC

TL;DR

Pathology inference has been reading a frozen, hand-generated CSV two dataset versions behind the rest of the repo, produced by a one-shot script hardcoded to one engineer's local VM cache — while `vista_bench`'s real pathology substrate (slide-linking, stain classification, LLM-extracted labels) only landed in vista_bench_v1_6. This plan bumps the shared VISTA_BENCH_DATASET constant to v1_6 (Phil's explicit call — whole-repo, not a pathology-only knob), re-verifies CT/EHR/text aren't broken by that bump as a gated prerequisite, then routes pathology through the same task-scoped BQ loader CT/EHR/text already use (Phil's feedback simplified this from a bespoke new manifest query down to pure reuse — diagnostic_tasks, zero new query code) and re-tiles whatever slide delta surfaces. No legacy baseline exists to byte-diff pathology against, so the landing gate is a human-QA render via the existing config-context viewer — the same mechanism Step 5 converged on.

▸ Phase 0 — Dataset bump + re-verify existing modalities PENDING

Bump VISTA_BENCH_DATASET v1_5→v1_6. Before touching pathology, confirm this doesn't silently break CT/EHR/text, which are pinned to v1_5-derived golden fixtures (including Step 5's just-landed live-EHR-adapter work). Cheap-before-expensive: a schema-diff first, a scoped byte-diff re-bank second.

Files: query_utils.py:257

Verify (Step 0a, cheap): BQ schema-diff comparing v1_5 vs v1_6 column lists for tables CT/EHR/text loaders actually read. Expected: no non-additive changes among CT/EHR/text-relevant columns. Stop: a breaking schema change — report back, don't proceed to 0b.

Verify (Step 0b, moderate, only if 0a clean): re-run diff_golden.py --mode strict against a small representative re-bank sourced from v1_6, banked to a new path. Expected: byte-identity holds for CT/EHR/text content. Stop: unexpected divergence — report back, don't proceed to Phase 1.

Decision gate: Phase 0 clean → Phase 1. Phase 0 red → STOP, re-plan.

▸ Phase 1 — Reuse existing task-scoped loader + coverage/tiling-gap characterization PENDING changed
Rewritten per Phil's OQ1 feedback: no new BQ query function — pathology reuses the same _load_task_data machinery CT/EHR/text already use.

Every other modality resolves its BQ table purely from task_source_csv in valid_tasks.json (WHERE task = @task_name). Since `vista_bench`'s pathology-tagged diagnostic-group tasks are already materialized into vista_bench_v1_6.diagnostic_tasks, pathology's task_source_csv almost certainly already resolves there — Step 1a confirms this against the live registry (that file lives on the VM, not this repo, so it isn't assumed). If confirmed, _load_path_task_data (run_bq.py:477) calls _load_task_data (run_bq.py:250-343) directly — zero bespoke pathology query code. Task-filtered rows are already one-per-person-per-task, so the dedup concern that originally motivated a separate manifest table doesn't apply. After live rows return, apply the existing PathologyAdapter.materialize(...) unchanged.

Files: run_bq.py (~477-548, rewritten to call _load_task_data)

Verify (Step 1a, cheap): confirm a pathology task's task_source_csv entry resolves to diagnostic_tasks. Expected: confirmed as assumed. Stop: resolves to something else — report back with the actual value, don't silently adapt.

Verify (Step 1b): exercise the rewritten loader for one pathology task (non-empty df, path_image_path populated) + a coverage report: old-CSV persons vs new persons (added/dropped), and a count of resolved path_image_path values with no existing tile folder under test_patch/. Expected: loader succeeds (same de-identified project/credentials CT/EHR/text already use). Stop: BQ access failure — unexpected, since this reuses an already-working credential path.

Decision gate (pre-encoded): no-local-tile count small (under ~10%) → Phase 2 is a quick top-up, stays on Claude-Code CPU. Large (most slides new) → Phase 2 is a real bulk job, routes to phil-hcpu, readback on phil-sllm-01.

▸ Phase 2 — VM-side re-tiling for the delta, gated on Phase 1 PENDING

Files: download_path_subsampled.py (minor default/doc tweak)

Verify: new tile folders appear under test_patch/<folder>/ for delta slides; no errors. Stop: systemic (not isolated-row) GCS/OpenSlide failures.

Destructive: no — additive only, no deletion of existing tiles.

▸ Phase 3 — Wire one, QA all three + docs PENDING changed
Updated per Phil's OQ2 feedback: "let's start with one but test all" — QA scope widened from just path_full to all three presets.

path_full stays the one actively wired/enabled preset in configs/all_tasks.yaml (matching today's production config), but QA-renders all three — path, path_image_and_report, path_full — via the existing config-context viewer, since the loader fix is shared code and all three should be confirmed working even if only one ships enabled. This is the landing gate: there's no legacy pathology baseline to byte-diff against. Update the three stale docs to describe the live-pull flow instead of the v1_3 CSV flow.
