# vista_eval_vlm — Step 5 re-plan #4: LOINC-scoped data-provenance investigation

**Status: Draft** (2026-07-20)

## Context

`feat/lumia-live-ehr-adapter`'s Step 5 (replace frozen `patient_string` CSV substitution with a
live LUMIA-XML render) has been through three rounds of class-3 deviations on its byte-diff gate,
each root-caused and fixed. Round 3 (`docs/plans/vlm-step5-lumia-window-scope-replan.md`) applied
a 24-month window crop to match legacy's actual scope — a large partial fix (live/legacy line
ratio 1.93→1.13, excess 7990→2779 lines) but the VM readback
(`docs/vm-status/2026-07-20-a58f5f9.md`, Step 1e) landed in **band 3**: `total_excess_lines=2779`
still exceeds the `~2500` "second unidentified cause" threshold, even though the ratio itself
(1.13) cleared its own `<=1.15` bar. Per the doc's own gate wording, this is "a narrower follow-up
investigation, not a full re-plan from scratch." The residual is overwhelmingly concentrated in one
domain: `full_excess_by_domain` shows **LOINC=2724** of 2779 excess lines (98%) — SNOMED (562) and
everything else are minor by comparison. The interval-split signature (round 2's mechanism) still
explains only 5.5% (153/2779), consistent with its earlier 4.0% refutation — closed, not worth
re-checking.

**Planner-side investigation this session (git archaeology + source reading across
`vista_eval_vlm`, `meds2text`, `meds_tools` — no VM/data access) exhausted the rendering-code
explanations and landed on a different kind of hypothesis than rounds 1-3:**

- Legacy's `patient_string` is generated by reading **raw MEDS events directly** from a frozen
  `meds_reader.SubjectDatabase` at
  `/home/rdcunha/vista_project/vista_bench/thoracic_cohort_meds/thoracic_cohort_meds_femr_db`
  (`src/data_tools/csv_helper/subsampled_retrieval_csv.py:29`, `DEFAULT_MEDS_DB` — set once
  2026-02-16 `b179579`, never touched since) via `meds_tools/patient_timeline.py::get_subject_events_df`
  — a **zero-transform** raw event dump (DataFrame construction + time-window slice + ontology
  description lookup only).
- Live's LUMIA `.xml` corpus lives at a **different path entirely**,
  `/data/fries/datasets/vista_bench_ryan/thoracic_cohort_lumia`
  (`configs/all_tasks.yaml:93`, `retrieval.corpus_dir`) — no shared ancestry visible from either
  repo. It's built via meds2text's own transform chain, whose only two relevant transforms
  (`delta_encode`, `remove_nones`) are **dedup/removal-only** — if anything they should make
  live's *true* volume smaller than a raw dump, not larger.
- Both paths converge on the same `get_llm_event_string` for final line rendering
  (`src/data_tools/utils/meds_timeline_utils.py`, byte-identical to `meds_tools`' copy) — one
  DataFrame row always yields exactly one output line; no duplication mechanism exists there.
- **No LOINC-specific code exists anywhere in the meds2text transform stack** (`grep -i LOINC`
  across all `.py` files = zero hits). LOINC's 98% dominance in the excess is very likely
  base-rate (labs are the single highest-frequency event domain in any oncology timeline), not
  evidence of a LOINC-targeted bug.
- Already exhausted/ruled out this round (don't re-investigate in round 4): `omop_split_interval_events`
  (measured at 5.5%, closed both rounds), `bin_events`/`fuzzy_partition`/`bin_by_time`
  (assign-once binning — can't duplicate events by construction), `delta_encode`/`remove_nones`
  (dedup-only, wrong direction), the two already-declared residual classes from round 2
  (zero-valued-numeric collapse, ontology-override collapse — both within-line content
  substitutions, not line-count inflators, orthogonal to this investigation).

**Leading hypothesis: legacy and live are drawing from two different underlying data
extractions/snapshots**, not the same MEDS data through two code paths. Notably, both source
directory names (`rdcunha`, `vista_bench_ryan`) trace to Ryan D'Cunha — the same person who
authored the 24mo-window commit round 3 found — so this may be the same person's two exports at
different times/scopes, not two unrelated data sources. That's a plausible-but-unconfirmed detail,
not evidence either way; it can't be resolved from code, only from data.

Since the rendering-code explanations are now exhausted (three rounds of git archaeology across
every plausible transform), round 4 pivots from *code archaeology* to a **direct, code-bypassing
data-provenance check on the VM** — the only way left to confirm or refute this hypothesis.

## Goal

Determine, from direct evidence, whether the residual ~2.7k-line LOINC excess reflects a genuine
data-source/vintage divergence between legacy's frozen MEDS snapshot and live's LUMIA corpus
(as opposed to a still-undiscovered render/adapter bug), and get a landing-gate decision for Step 5
based on that answer.

## Approach

Two cheap VM checks, in order of how conclusive each is — no code changes to land first (this is
investigation-only; nothing here modifies `ehr.py`/`presets.py`/`run_bq.py`).

**Step 1 — provenance metadata scan (cheap, no PHI, seconds of work).** meds2text's own transform
pipeline stamps MEDS-format datasets with `metadata/dataset.json` containing `transform_name`/
`post_etl_version` (`meds2text/src/meds2text/transforms/core.py:402-413`). Check whether an
equivalent metadata file exists next to `thoracic_cohort_meds_femr_db` (legacy's source) and
whatever MEDS dataset was the input to the `thoracic_cohort_lumia` XML build (check the LUMIA
corpus root/parent for a metadata file, build log, or README). If both exist and show different
OMOP-extraction dates/versions, that's a fast, direct confirmation. If either is missing, that's
an expected possible outcome (not a Stop) — Step 2 is the conclusive test regardless of whether
this step lands cleanly.

**Step 2 — raw LOINC event-count check, bypassing all rendering/adapter code (the real test).**
Reuse the **existing 20-row `lumia_live_windowed`/`legacy_small_v2` banks already on disk from the
round-3 VM run** — pull `person_id` from each of the 20 already-banked rows (no new
`golden_harness` run, no new person selection). For each of the 20 persons, count LOINC-domain
events in each **raw** source within the same 24-months-before-`embed_time` window used
everywhere else on this branch:

- **Legacy side:** `meds_reader.SubjectDatabase(DEFAULT_MEDS_DB)[person_id].events`, filtered to
  `code.startswith("LOINC/")` and `time` within the window. Same database object the
  `subsampled_retrieval_csv.py` generator itself uses.
- **Live side:** `context.adapters.ehr.parse_lumia(context.adapters.ehr.lumia_path_for(person_id,
  corpus_dir))` — this is already the *raw* XML→DataFrame parse step with **zero** filtering/
  dedup/windowing applied (confirmed by reading `parse_lumia`, `src/context/adapters/ehr.py:201-247`:
  it only builds rows and sorts chronologically — no collapsing logic of any kind lives there; all
  of that is in `ehr_filters.py`'s `EHRAdapter.filters`, which this step deliberately bypasses).
  Filter the returned DataFrame to `code.startswith("LOINC/")` and the same time window.
- `embed_time` per person: load via the existing `TaskOrchestrator._load_task_data` pattern already
  used in the round-3 doc's Step 1b precondition check, restricted to the 20 already-selected
  person_ids.

Report only aggregate counts across the 20 persons (total raw legacy LOINC count, total raw live
LOINC count, ratio, and the same total split by min/median/max-per-person to catch a single
outlier skewing the aggregate) — **never person_ids** in the readback, matching this branch's
PHI-discipline convention throughout.

This test is far more conclusive than Step 1 regardless of what Step 1 finds: it isolates the
question to "does the raw source data actually differ in LOINC volume" with **zero** rendering or
adapter code in the loop — if the same ~1.1-2.7k-scale gap reproduces here, no further code
archaeology can explain it (there's no code left in the loop to blame). If it doesn't reproduce, a
render/adapter bug is confirmed to remain and round 4's negative result is itself useful — it
rules out the data-provenance hypothesis cleanly and re-focuses round 5's search.

## Decision gate (proposed default — flagged below as an Open Question for Phil, not auto-decided)

- **Step 2's raw counts show a comparably large gap** (live's raw LOINC total well in excess of
  legacy's raw LOINC total across the 20-person sample, roughly consistent with the already-observed
  rendered-line-level pattern) → confirms data-source/vintage divergence. Recommended default:
  accept as a **declared, permanent divergence** (same treatment already given to STANFORD_OBS),
  add a scoped `diff_golden.py` exclusion if needed for the byte-diff gate to read as intentional
  rather than failing, and — this is the bigger call — **pivot Step 5's landing gate to rely on
  Phase 2's human visual-QA read** (`context_viewer.py`, already-built, never yet completed on this
  branch) as the primary correctness check for EHR content, rather than continuing to chase full
  byte parity against a legacy baseline that may not represent the same underlying data pull.
- **Step 2's raw counts show near-parity** (gap doesn't reproduce when reading directly from both
  raw sources) → refutes the data-provenance hypothesis. STOP, hand back to the Mac — a real,
  still-undiscovered render/adapter bug remains; round 4 didn't find it, don't guess further absent
  new evidence.
- **Step 1 alone surfaces a conclusive, explicit provenance mismatch** (different extraction dates/
  versions in both metadata files) → still run Step 2 to corroborate at the LOINC-domain level
  specifically (Step 1 is dataset-wide provenance, not domain-specific) — Step 1's finding can
  shortcut *interpretation* of Step 2's result but doesn't replace running it.

N=20 is a real sample (not a 2-person spot check — free to compute since it reuses already-banked
person_ids and `parse_lumia` is cheap), but still not a rigorous statistical test. Report the
numbers plainly; Phil makes the final call on the disposition given the actual figures rather than
this doc pre-committing to a rigid numeric threshold on N=20.

### Step 2 — raw LOINC event-count check across the 20 already-banked persons

```bash
cd <repo-root>/vista_eval_vlm/src
python3 -c "
import pandas as pd
import meds_reader
import json

from context.adapters.ehr import parse_lumia, lumia_path_for
from vista_run.run_bq import TaskOrchestrator

MEDS_DB = '/home/rdcunha/vista_project/vista_bench/thoracic_cohort_meds/thoracic_cohort_meds_femr_db'
CORPUS_DIR = '/data/fries/datasets/vista_bench_ryan/thoracic_cohort_lumia'
LIVE_BANK = '<results_dir>/golden/.../progression_recurrence_free_survival_1_yr_no_image_lumia_live_windowed_golden.jsonl'

# Pull the 20 already-selected person_ids from the round-3 bank -- no new selection.
person_ids = []
with open(LIVE_BANK) as f:
    for line in f:
        rec = json.loads(line)
        person_ids.append(rec['person_id'])
assert len(person_ids) == 20, f'expected 20 rows, got {len(person_ids)}'

orch = TaskOrchestrator('<ABS_PATH_TO_configs/all_tasks.viewer.vm.yaml>', 'gemma3', 'google/medgemma-1.5-4b-it')
task_info = next(t for t in orch.valid_tasks if t['task_name'] == 'progression_recurrence_free_survival_1_yr')
df, timeline_col, source_csv = orch._load_task_data(task_info, use_no_report_csv=False, require_timeline=True)
embed_times = df.set_index('person_id')['embed_time'].to_dict()

database = meds_reader.SubjectDatabase(MEDS_DB)

legacy_counts, live_counts = [], []
for pid in person_ids:
    embed_time = pd.to_datetime(embed_times[pid])
    window_start = embed_time - pd.DateOffset(months=24)

    subj = database[pid]
    n_legacy = sum(
        1 for event in subj.events
        if str(event.code).startswith('LOINC/') and window_start <= pd.to_datetime(event.time) <= embed_time
    )
    legacy_counts.append(n_legacy)

    xml_path = lumia_path_for(pid, CORPUS_DIR)
    live_df = parse_lumia(xml_path)
    if live_df.empty:
        live_counts.append(0)
    else:
        mask = (
            live_df['code'].astype(str).str.startswith('LOINC/')
            & (live_df['time'] >= window_start) & (live_df['time'] <= embed_time)
        )
        live_counts.append(int(mask.sum()))

total_legacy = sum(legacy_counts)
total_live = sum(live_counts)
print(f'n_persons={len(person_ids)}')
print(f'total_legacy_raw_loinc={total_legacy}')
print(f'total_live_raw_loinc={total_live}')
print(f'raw_ratio={(total_live/total_legacy) if total_legacy else float(\"nan\"):.2f}')
print(f'per_person_legacy: min={min(legacy_counts)} median={sorted(legacy_counts)[len(legacy_counts)//2]} max={max(legacy_counts)}')
print(f'per_person_live: min={min(live_counts)} median={sorted(live_counts)[len(live_counts)//2]} max={max(live_counts)}')
"
```

**Expected:** prints the aggregate counts above. Compare `raw_ratio` against the already-observed
rendered-line ratio context (LOINC excess was 2724 lines across these same 20 rows) — a
similarly large raw-level gap is the confirmatory signal for the data-provenance hypothesis; a
raw ratio near 1.0 refutes it.
**Stop:** any exception (missing files, `KeyError` on `embed_time`/`person_id`, empty
`SubjectDatabase` lookup) — report the exception type/message only (no data payload), hand back to
the Mac; do not silently skip persons and report a partial aggregate as if it were complete.
**Destructive:** no — read-only queries against existing databases/files, no writes.
