TL;DR

Live LUMIA rendering (timeline variant, used by no_image/axial_all_image) currently renders each patient's entire clinical history with no time window, while the frozen legacy patient_string comparator was generated with a 24-month lookback from embed_time. That scope mismatch — not a meds2text render bug — explains most of the ~2x event-volume gap the 2026-07-20 VM run found (the leading interval-split hypothesis explained only 4.0%).

Fix: give the timeline variant the same kind of window filter no_img_report already has, defaulting to 24 months (config-overridable), then re-run the byte-diff gate to confirm the gap collapses. Phil wants this crop applied in production, not just to pass the diff.

Gotchas

No separate "restricted person_id CSV" ever existed

Earlier plan drafts referenced reusing a restricted-input artifact from 2026-07-18/20. It never existed as a distinct file — the actual mechanism was the plain all_tasks.viewer.vm.yaml config at 100% coverage (1238/1238), which already draws identical index sets on both sides. Confirmed via docs/vm-status/2026-07-18-phase1-demographics-fix-rerun.md:141-143.

window() silently no-ops on missing embed_time

ehr_filters.py:73 — if embed_time is null, window() returns the DataFrame unchanged, silently preserving the exact unbounded-history bug this plan fixes. Phase 1 adds an explicit non-null anchor-coverage check for this reason.

Config override must land before EHRAdapter(config=...) is constructed

EHRAdapter.__init__ resolves filters immediately (ehr.py:264) — mutating the block's config after construction is a no-op. The override in _apply_ehr_adapter must happen before that call.

"6 months" in the legacy comment is dead history — 24 months is real

subsampled_retrieval_csv.py:180 computes a 24-month window; the neighboring comment still says 6 months. Git blame (6a4c2ead, 2026-02-18, Ryan D'Cunha) shows this was a deliberate code change with the comment simply never updated. 24mo is what legacy has actually been producing since that date.

no_img_report's 6mo window is intentionally left hardcoded

It reproduces a different legacy comparator's contract than the one this fix targets. Don't generalize the config mechanism to cover it until there's a real request — see Approach 4.

Characterization script is pasted in-plan, not in $CLAUDE_JOB_DIR/tmp/

The 2026-07-20 handoff's fixed script lived at a per-job scratch path that isn't durable across sessions. This plan pastes the corrected script directly in Phase 1 so a fresh executor can run it without depending on prior job state.

golden_harness / diff_golden have no bare console-script entry

Both must be invoked as python -m vista_run.golden_harness / python -m vista_run.diff_golden from the src/ directory — there's no [project.scripts] entry in pyproject.toml. golden_harness also takes --config + --experiments (plural), not --experiment/--input.
