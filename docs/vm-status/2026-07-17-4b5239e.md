### OQ resolution 1 — `<person>` block structure & repetition

- **`<person>` is present in 100% of sampled files** (5 files, 11–185 encounters each) and is a child
  of **every** `<encounter>` (parent-tag histogram: `{encounter: N}` for all N encounters) — i.e. a
  sibling of the events wrapper, exactly as `markup.md` documents. **The Phase 0.5 STOP condition
  (`<person>` missing entirely) did NOT fire.**
- Structural skeleton (tag/attr **names** only): `person` → `birthdate`, `age`(→`days`,`years`),
  `demographics`(→`ethnicity@code`, `gender@code`, `race@code`), `payerplan`.
- **Repetition:** `<person>` repeats once per encounter, but the **stable demographic fields**
  (`birthdate` + `ethnicity`/`gender`/`race` code+text) are **identical across all encounters** —
  distinct-signature count = **1 per patient** in all 5 files. Only `<age>` (encounter-relative)
  varies, which is why a naïve whole-block hash showed all blocks distinct. → **Dedup is trivial:
  read demographics from any one `<person>` (e.g. the first encounter); no cross-encounter merge
  needed.**

### OQ resolution 2 — Race field presence

- **Race IS present in source XML** — `<demographics>/<race code=…>…</race>` in 100% of sampled
  files, alongside `<ethnicity>` and `<gender>` (each carries both a `code` attr and element text).
- → **This resolves the re-plan's Open Question #3 the *opposite* way from its tentative fallback:**
  Race is **synthesized alongside** ethnicity/gender (Approach #2), **not** added to the
  accepted-divergence list. The `--exclude-line-patterns` flag needs **only** `STANFORD_OBS/Flowsheet`,
  not `Race`.

### OQ resolution 3 — exact demographic render conventions (from the already-banked legacy golden)

Source: `…/medgemma-1.5-4b-it/progression_recurrence_free_survival_1_yr_no_image_legacy_small_golden.jsonl`
(20 rows, banked in the prior handoff). Rendered lines matched against the same patient's `.xml`
`<person>`. All values masked; only format/relationship reported.

- **Render shape** (per `get_llm_event_string`, `meds_timeline_utils.py:214-232`): each line is
  `[YYYY-MM-DD HH:MM] | {code}{ (description)}` — demographics carry **no** description, no VALUE, no NOTE.
- **`MEDS_BIRTH`** — bare code, **no description**; timestamp = the `<birthdate>` (date match **13/13**).
  Legacy emits it **twice** per patient (MEDS_BIRTH line-count = 2 for **13/13** demographic-bearing patients).
- **`Gender` / `Race` / `Ethnicity`** — `code` = the XML `<demographics>/<tag>` **`code` attribute
  verbatim**, which is already in `Class/<omop_concept_id>` form (e.g. `Gender/8532`, `Race/8527`,
  `Ethnicity/38003564`). Legacy-token == xml-code-attr **verbatim 39/39**; **no description** (0/39
  had parens). *(Earlier mismatch was a test artifact — the attr already includes the `Class/` prefix,
  so no re-prefixing is needed at synthesis.)*
- **Timestamp anchor** — all Race/Ethnicity/Gender lines are anchored at the **birthdate** timestamp
  (== MEDS_BIRTH ts, **39/39**).
- **Intra-birthdate order** — consistent across **13/13** patients:
  **`MEDS_BIRTH, MEDS_BIRTH, Ethnicity, Race, Gender`**. Because birthdate is the earliest time,
  `parse_lumia`'s existing stable chronological sort places these at the top of the timestamped event
  stream (legacy renders them at fixed lines 15–19, after a ~15-line non-timestamped preamble; the
  render is globally ascending-by-displayed-ts 20/20). → **Synthesis should append rows in that exact
  order (2× MEDS_BIRTH, then Ethnicity, Race, Gender) all at time=birthdate**, and the stable sort
  will land them correctly.

### ⚠️ NEW asymmetry the fix design must handle (not a STOP — flagged for the Mac)

- **7 of 20 legacy golden rows carry NO demographic lines at all**, yet **all 7 have a full
  `<person>` + birthdate + demographics in the XML source** (verified 7/7). So this is a **legacy-side
  omission** (patient_string vintage), not a source gap.
- **Implication:** synthesizing demographics from `<person>` (always present) will give the *live*
  render demographic lines for **all** patients, including these 7 — which legacy lacks. Even a
  byte-perfect synthesis will therefore **newly diverge** on those 7 (live has the demo block, legacy
  has nothing there). This is a *different direction* of divergence than STANFORD_OBS (there, legacy
  has extra lines; here, live has extra lines).
- **Not an executor call to resolve** — the Mac should decide the acceptance treatment, e.g.:
  (a) accept it as another declared, expected divergence (live is the richer/correct render), or
  (b) restrict Phase 1's byte-diff gate to the demographic-bearing legacy subset, or
  (c) treat the demographic pseudo-events as themselves subject to `--exclude-line-patterns` on the
  legacy comparison. This bears directly on whether Phase 1's byte-diff can reach `ALL GATES PASS` or
  whether the residual is inherently non-zero for the ~35% of patients legacy left demographic-less.
